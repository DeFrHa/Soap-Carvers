# Build Crew – notes for Claude / contributors

A wonky first-person "friendslop" co-op building game (working title; replaces
the Soap Carvers prototype, which lives on in git history). A truck dumps an
unsorted PHYSICS pile of building parts. The crew sorts it onto pallets,
prepares parts (saw, cut glass, mix mortar) and assembles a building from a
blueprint before the timer runs out. Then a final test (wind, rain) shows
what was built badly. Single player now, built so a network layer (Netcode
for GameObjects or FishNet) can be added later.

## Project owner notes

- Unity version: 6000.3.6f1, 3D, URP, new Input System.
- Put all scripts in `Assets/Scripts`.
- Commit directly to `main`.

## Tech

- **Unity 6000.3.6f1**, **URP**, **new Input System** (actions are built in
  code; the template's `.inputactions` asset is unused), C#.
- UI uses **UGUI with legacy `UnityEngine.UI.Text`** and the built-in
  `LegacyRuntime.ttf` font, so the TextMeshPro essentials import isn't needed.
- No external assets or packages beyond URP, Input System and UGUI.
- Everything visual comes from Unity primitives and code-built meshes and
  materials (`MaterialPalette`, `MaterialFactory`). Part visuals are combined
  into one mesh per part (`PartVisualBuilder`).

## Hard rules

1. **Every object is a dynamic Rigidbody with realistic mass, all the time.**
   Parts, tools, buckets, the ladder, the wheelbarrow, pallets, the tool rack,
   the mortar station, shards. Only the ground/bumps are static, and only the
   truck (and the players' hand anchors) are kinematic. **Never parent a held
   object to the camera** and never make it kinematic: holding is a joint.
2. **Holding is a physics grab.** `Grabbable.AttachGrabber` adds a
   ConfigurableJoint at the grabbed point, connected to the grabber's kinematic
   hand body (`PlayerGrabber`). Linear drive: spring `mass * f^2`, capped at
   `grabStrength`; slerp drive capped at `grabMaxTorque`. Several grabbers =
   several joints whose forces add up. Weight classes (light / medium / heavy)
   follow from mass vs. strength. Tools are grip items: grabbed at their grip
   and held in a pose in front of the camera (the hand rotates, the joint
   follows). A joint keeps the relative rotation it had when created, so to
   turn something you rotate the anchor body, never set `targetRotation`.
3. **Every state change goes through a command.** Players and the simulation
   build a `GameCommand` (plain data: ids, numbers, vectors) and call
   `CommandBus.Execute`; managers register one handler per type and the bus
   logs every executed command. Grab/Release/Place → `GrabManager`; Snap/
   Unsnap/Fix → `BuildManager`; Cut/Break → `PartManager`; ingredients, mixing,
   mortar, spills, handfuls of nails → `WorkshopManager`. Round flow goes
   through `GameManager.Request*`. This is where networking will sit: clients
   send commands, the host executes them. Commands reference objects by
   `EntityRegistry` id (scene objects get fixed ids from `SceneBuilder`;
   runtime spawns get ids ≥ 100000 from the host).
4. **Input is separate from actions.** `PlayerInputHandler` only reads devices.
   `PlayerActions`, `PlayerMotor`, `PlayerLook` consume its values; tools get a
   `ToolInput` struct. A remote player simply won't have an input handler.
5. **No static singletons for player-specific state.** `World` caches the
   world managers (one per scene) via `FindFirstObjectByType`; per-player state
   (hand, pockets, held object) lives on the player object. Player id lives on
   `PlayerGrabber.PlayerId`, team on `PlayerGrabber.TeamId`.
6. **Building physics.** A snapped part hangs on a SOFT ConfigurableJoint to a
   kinematic anchor at its slot (raised by the static sag `g/f^2`). Fixing
   replaces it with FixedJoints (with `breakForce`) to the parts in the slots it
   `restsOn`, or to the world for ground slots. The building stays fully
   physical; broken joints make a part loose again (`UnsnapCommand`). A slot
   only accepts a part when everything it `restsOn` is fixed.
7. Tools only work in the Build state (`Tool.ToolsEnabled`); the ladder and
   tablet always work.
8. Shards, camera shake and similar effects are cosmetic and
   non-deterministic. Keep them out of game state. Joint/rigidbody poses are
   physics state (a future network transform), not command state.

## Kits (data-driven)

- A kit is a JSON file in `StreamingAssets/Kits`: `id, name, description,
  roundTime, finalTest ("wind" | "windRain"), stages[], slots[]`. A slot is
  `id, partType, size, position, rotation (Euler), stage, fixMethod
  ("nails" | "screws" | "mortar"), restsOn[]`, in build-site local meters
  (x right, y up, the building's FRONT faces -z). Box sizes are in the part's
  local frame; linear parts (post, plank, beam) run along local x.
- The two built-in kits are designed in code (`KitDesigns`) and written by
  **Build Crew → Generate Kit JSONs** (or `Tools~/kit-gen/run.sh` offline,
  which also checks overlaps and restsOn contacts). Do not hand-edit those two;
  change `KitDesigns` and regenerate. `KitLoader` falls back to `KitDesigns`
  if a built-in file is missing.
- Choose the kit with the **Kit** dropdown on the GameManager, or set
  **Custom Kit File** to load any JSON in `StreamingAssets/Kits`.
- `PileGenerator` delivers STANDARD sizes: posts 2.5 m, planks 2/3 m, beams
  3/4 m (first-fit-decreasing packing, so shorter pieces must be cut), panes
  1 x 1 m, ready-made parts as-is; plus `sparePercent` spares, wrong-length
  decoys, a toilet, a gnome and boxes of nails/screws.

## Scene generation

- The scene is generated, not hand-built. To change the layout, edit
  `SceneBuilder` and re-run **Build Crew → Create Playable Scene**, which
  overwrites `Assets/Scenes/BuildCrew.unity` and the materials, writes missing
  kit JSONs and keeps `GameSettings.asset` if one exists.
- `GameBootstrap` on an empty GameObject builds the same scene at runtime.
- `SceneBuilder` builds under an inactive root and detaches objects managers
  first, so components can rely on their serialized refs and the managers in
  `Awake`. Cross-object initialisation that needs another object's `Awake`
  belongs in `Start`. Command handlers register in `Awake`; commands are only
  sent from `Update` on.
- The scene supports N `TeamArea`s (truck + pile, pallets, build site, final
  test camera, blueprint studio, spawn); `SceneBuilder.BuildTeamArea` makes one.
- Layer: `Hologram` (preferred index 31; `Layers.Hologram` falls back to 31 if
  it is unnamed). The main camera excludes it; the blueprint camera renders
  only it.

## Conventions

- Unity 6 APIs: `FindFirstObjectByType`/`FindObjectsByType`,
  `Rigidbody.linearVelocity`/`linearDamping`, `PhysicsMaterial`. Avoid
  deprecated APIs. Don't use `?.` on UnityEngine.Object references.
- One MonoBehaviour/ScriptableObject per file, file name = class name. Plain
  command/data classes may share a file (`*Commands.cs`, `BuiltInParts.cs`).
- Comment the non-obvious math (joint springs, wind load, packing), not the obvious.
- Tunables go in `GameSettings` (grab strength, snap distance, saw strokes,
  mortar ratios, wind...). Kit-specific values go in the kit JSON.
- Coordinates: team area 0 at the origin, pile around z = 6, truck parks at
  z = 13, build site at z = -11 rotated 180° (front faces the pile), player
  spawns at z = -1 facing +Z.

## Extending

- **New part type:** subclass `PartDefinition` (look, mass, stock lengths,
  cut tool, colliders) and `PartCatalog.Register` it; kits refer to it by `Id`.
- **New tool:** subclass `Tool` (or `FixingTool`/`CuttingTool`), implement
  `Use()` and/or `WhileUsing`, send commands, add a `Build<Tool>` method in
  `SceneBuilder` with a grip and hold pose.
- **New kit:** design it in `KitDesigns` (built-in) or drop a JSON into
  `StreamingAssets/Kits` (community).
- **Two-person tools:** see `PartManager.ReportSawing/SawyersOn` (the
  two-person saw hook); the same pattern works for any tool that wants a buddy.

## Checking code without Unity

- `Tools~/compile-check/run.sh` compiles `Assets/Scripts` against Unity 2021.3
  reference DLLs from NuGet, with an Input System stub. Unity 6 names are
  shimmed, so it catches syntax, type and naming errors but not Unity 6 API
  drift. Needs the dotnet SDK. Run it before every push.
- `Tools~/kit-gen/run.sh` runs `KitDesigns` + `PileGenerator` on plain .NET,
  validates the kits (ids, restsOn, cycles, overlapping slots, restsOn pairs
  that don't touch, floating ground slots), prints the pile and writes the JSONs.
- Always also check in the real editor.
